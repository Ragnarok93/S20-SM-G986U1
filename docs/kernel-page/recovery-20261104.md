## 4. Crash records

Dropbox holds exactly three `_KP` entries, one per loss, and no others:

| entry | written | loss |
| --- | --- | --- |
| `SYSTEM_LAST_KMSG_399_…_101957_KP` | 10:19:57 | 10:09 |
| `SYSTEM_LAST_KMSG_400_…_190448_KP` | 19:04:48 | 18:46 |
| `SYSTEM_LAST_KMSG_401_…_202100_KP` | 20:21:00 | 20:02 |

All three contain the same bootloader line:

```
collect_rr_data : upload_cause = KERNEL PANIC ( panic_msg = Oops PC = rt_mutex_adjust_prio_chain+0x304/0x858 )
```

That is the faulting PC for every loss, recorded by the crash-dump collector
rather than inferred. `rt_mutex_adjust_prio_chain` is the walk the route targets,
and `+0x304` is the offset the earlier image differential was trying to move
(ledger row 8): it did not move.

The captures also hold per-CPU context saves for the idle CPUs
(`lpm_cpuidle_enter`), `sec_debug_panic_handler`, and
`sec_debug_pm_restart: rebooting...`. The faulting CPU's own register dump and
the oops text are not readable in the dump. pstore, `dmesg`, `/proc/last_kmsg`
are permission-denied; `logcat -b crash` is empty.
