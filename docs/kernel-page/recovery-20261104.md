| `SYSTEM_LAST_KMSG_401_…_202100_KP` | 20:21:00 | 20:02 |

All four contain the same bootloader line:

```
collect_rr_data : upload_cause = KERNEL PANIC ( panic_msg = Oops PC = rt_mutex_adjust_prio_chain+0x304/0x858 )
```

That is a common reported faulting PC, recorded by the crash-dump collector rather
than inferred. It does not by itself establish that the route caused the panic:
the location is relevant because the route exercises the PI-chain machinery, but
causation needs the instruction and its execution context. `+0x304` is the offset
the earlier image differential was trying to move (ledger row 8): it did not move.

The entry timestamps above are **record-creation times**, written after the
reboot, not fault times. The 20:02 boot bracket in §2 is the separate and
stronger temporal evidence.
(`Oops PC` is printed by the running kernel's own symbol resolution, so the
symbol and offset are device-authoritative even though the instruction is not.)

The captures also hold per-CPU context saves for the idle CPUs
(`lpm_cpuidle_enter`), `sec_debug_panic_handler`, and
`sec_debug_pm_restart: rebooting...`. The faulting CPU's own register dump and
the oops text are not readable in the dump. pstore, `dmesg`, `/proc/last_kmsg`
are permission-denied; `logcat -b crash` is empty.

## 8. Resolving `+0x304`

**Resolved** in `symbol-resolution.md`: `+0x304` is `ldr x8, [x8, #56]`, the
`w->lock` read inside `rt_mutex_top_waiter()` (`rtmutex_common.h:52-63`),
inlined at `rtmutex.c:661`. The method below is what the resolution followed,
kept here so a later reader can re-run it on another build:

1. Verify the artifact's identity against the device: version string, build
   identity and symbol table, not just the source release.
2. Resolve `rt_mutex_adjust_prio_chain` to its symbol address.
3. Add `0x304` and disassemble around that address, keeping instructions on both
   sides.
4. Map the instruction back to `kernel/locking/rtmutex.c` and inspect the pointer,
   lock and task state it touches.
5. Treat any recovered register or stack context from the three dumps as separate
   corroboration, not as a substitute for the instruction.

What was checked, and what could not stand in:

| candidate | identity | verdict |
| --- | --- | --- |
| `~/s20_kernel_chxl1/out-stock-layout/vmlinux` | `Linux version 4.19.113 (ubuntu@DESKTOP-…) … Wed Oct 28 06:17:31 CDT 2026`, BuildID `e17e6942…`, with debug_info | **a local rebuild** — the device runs `#1 SMP PREEMPT Fri Dec 27 14:53:28 KST 2024`; not the device build |
| same tree's `System.map` | `rt_mutex_adjust_prio_chain = ffffff8008146c04`, `_text = ffffff8008080000` | symbol addresses for that rebuild only; never to be combined with the device's offset |
| device `/proc/kallsyms` | `Permission denied` for the shell | no on-device layout check is possible |

The resolution was already in reach without the vendor's unstripped `vmlinux`: the
stock kernel inside this device's own `boot.img` carries the kallsyms table that
formatted the panic, and its bytes disassemble. The image's build string and the
printed `/0x858` size both matched before any instruction was read. A `System.map`
alone would still not be enough, and neither would a rebuild: compiler version,
configuration, vendor patches and link layout all move instruction offsets, and
this rebuild's version string differs from the device's by almost two years.
